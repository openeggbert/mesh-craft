This plan combines two independent investigation passes run in the same session: (1) five parallel forked audits covering mc3/mcb, mc3togltf/mc3tomcb, the editor application, the renderer+web+platform layer, and tests/CI/docs, plus a direct manual pass over the exporter/converter tools; and (2) an earlier direct manual investigation (file-size sweep, TODO grep, targeted reads) that ran before the forks landed and found a few things the forks didn't — notably a second dual-implementation risk (primitive geometry) structurally identical to the project's already-known CSG dual-path issue. # Deep Audit Summary

**Current project state**: MeshCraft is a mature, already-heavily-stabilized C++23 codebase (650 `STAB-XXXX` tasks in `plan.md`, 620 ✅). The native Linux build is clean and 66/66 tests pass **as of AUDIT-0052's fix this session** — a truly-fresh `ninja` rebuild (not the pre-existing incremental `cmake-build-debug/`) turned up a real, previously-unnoticed break caused by an upstream `../cna` API change (`Viewport::X`/`Y` field→property conversion), fixed with a 2-line call-site update in this repo. This is the third time this exact "incremental build dir silently masks a real break" failure mode has bitten this project (see `NEXT.md` §2/§4's own prior lesson) — this time for native Linux, previously assumed the one rock-solid configuration. Two other build targets remain broken for reasons entirely outside this repo (Windows/MinGW: `../cna` GLES3 gap + `../sharp-runtime` `-Werror` issues; Emscripten/web: a newly-found `../sharp-runtime` regression, see `web_issues.md`). Given that maturity, this audit did **not** find systemic rot — it found the class of bug you'd expect a second, fresh pair of eyes to catch in a well-maintained codebase: small silent-failure paths, one real cache-invalidation bug, a second undocumented dual-implementation risk, missing hardening in a few places that had a sibling already hardened, a couple of doc/reality mismatches, and one broken first-run instruction.

**Strongest parts**: the `mc3`/`mcb` core libraries (deterministic output via ordered `std::map`/`std::set`, clean CNA-free separation, already-hardened MCB size/recursion guards from a prior session, zero raw `new`/`delete` anywhere in first-party source — consistent RAII/smart-pointer discipline). The CSG exporter (`mc3togltf/src/CsgEvaluator.cpp`) — genuinely excellent defensive coding: every unsupported case throws a specific, actionable error message pointing at the `--allow-approximate-csg` escape hatch, rather than silently producing wrong geometry. Dirty-state/undo tracking in the editor is solid (only one small bug found in ~127 call sites checked). Reparent-cycle protection and drag-drop file-type validation are both already correct. Backend abstraction (EASYGL/SDL_RENDERER/BGFX/VULKAN) is 100% clean in application code — zero backend-specific branches outside CNA itself. Test registration hygiene is good: all 66 CTest tests are properly registered, no orphaned test binaries. Prior sessions' documentation of known gaps (`NEXT.md` §5, `plan.md`'s 🟡 rows) is honest and precise — every flagged item cross-checked this session held up as accurately described.

**Weakest parts**: (1) silent-failure paths in the editor — autosave, recent-file-open, and (new, cross-cutting) every `saveToFile()` in `mc3`/`mcb`/`mc3togltf` writes directly to the destination with no atomic temp-file-then-rename, so a crash or write failure mid-save can leave a truncated/corrupt file at the path the user asked to save to. (2) One real, silent rendering-correctness bug: the CSG preview cache's content hash omits `csgOperation`, `extrude`, and `meshSource`, so certain edits (e.g. switching a CSG group from Union to Difference without touching geometry) show a stale, wrong preview. (3) A **second, previously-undocumented dual-implementation risk**: primitive-shape geometry is generated independently by `mc3togltf/src/MeshBuilder.cpp::buildPrimitive()` (export/CSG path) and `SceneRenderer`'s unit-mesh+scale+LOD dispatch (editor preview path) — structurally the same risk class as the already-documented CSG dual-path invariant ("a missing cutter flag silently turns a subtraction into a union — this has bitten real test fixtures before"), but never itself flagged anywhere. (4) A false claim in `README.md`'s Platform Support Matrix — it says web builds persist prefs via IDBFS; they don't, `-lidbfs.js` is linked but `FS.mount`/`FS.syncfs` are never called anywhere. Two other matrix rows (native-build-success, viewport-rendering-status) are also now stale relative to this session's earlier findings in `web_issues.md`. (5) `README.md`'s own first build command (Linux, primary path) is missing `-G Ninja` and will fail as literally written for a new contributor. (6) `PropertiesPanel.cpp` and `MeshCraftApplication_UiLeftPanel.cpp` are two independent material-editing UIs by documented design, but nobody has ever actually verified whether they've *already* silently drifted apart in available properties/ranges/validation.

**Highest-risk areas**: the CSG cache-invalidation bug (AUDIT-0020) and the primitive dual-path risk (AUDIT-0011/0012) are the two highest-risk findings — both are "silent divergence" classes of bug that produce a *visibly plausible but wrong* result, the worst kind to leave unfixed, and both match a failure mode the project has already been bitten by once (per `NEXT.md`'s own CSG dual-path note). The non-atomic-save pattern (AUDIT-0019) is next — low probability, high blast radius (silent data loss on the exact operation the user trusts most).

**Best next implementation areas**: docs/build-instruction fixes (near-zero risk, immediate value), the CSG cache-key fix, the silent-failure fixes in the editor, the primitive dual-path documentation + cross-check test, and the MCB hardening-parity fixes (mechanical, mirrors an already-established pattern from commit `865d015`).

**Tasks safe for autonomy**: the large majority — see `Status: pending` rows below.

**Tasks requiring human decisions**: AUDIT-0037 (id-collision policy across includes), AUDIT-0038 (MCB version-migration policy), AUDIT-0039/0040 (CI matrix scope decisions). None of these were guessed at or implemented.

**Tasks blocked by external repos/environment**: AUDIT-0041 (UiOverlays.cpp mechanical split — needs a live display to verify ImGui layout survives, same class of blocker as the already-tracked `plan.md` STAB-0617) and AUDIT-0050 (implement real IDBFS persistence — code can be written but cannot be verified until the `../sharp-runtime` Emscripten build regression in `web_issues.md` is fixed upstream).

**On task count**: this audit produced **50 real, distinct, file:line-verified tasks**, not the suggested 150+. That reflects the codebase's actual state (already audited across 650 prior tasks) rather than a shallow pass — padding to a round number with near-duplicate or trivial busywork tickets would violate the explicit "do not create fake filler tasks" instruction this plan was created under. Where a finding genuinely decomposes into independent, separately-committable units (the 11 MCB reserve-ceiling call sites, the 8 files needing `ImGuiSliderFlags_AlwaysClamp`), it was split into that many tickets; where splitting further would just multiply near-identical one-line diffs (e.g. all 127 individual slider call sites), the audit's own judgment (confirmed independently by two separate review passes) was to keep it at file-level granularity.
